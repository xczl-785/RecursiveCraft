# RecursiveCraft NBT 实施路线图

> 目标分支：`1.20.1`
> 文档日期：2026-05-31
> 文档定位：用于定义 NBT 完整方案的实施阶段、各阶段目标、范围边界、完成标准与阶段间衔接关系

---

## 一、路线图定位

本路线图不是讨论过程记录，而是：

- **NBT 完整方案的实施路线图**

它回答的是：

1. 最终要做到什么
2. 每个阶段要做什么
3. 每个阶段不做什么
4. 每个阶段完成后要达到什么状态
5. 各阶段如何衔接

---

## 二、最终目标

最终目标定义为：

**完成 RecursiveCraft 的 NBT 完整方案，并按明确路线图分阶段落地。**

这里的“完整方案”包括：

1. 总体架构路线
2. NBT 材料身份标准
3. 共享库存抽象层
4. 第一阶段运行时 NBT 落地
5. 方案与代码对照
6. 后续扩展路线评估

---

## 三、总体原则

### 3.1 规划与实施分离

当前阶段可以把规划目标拉到完整方案；
实施阶段必须按阶段严格控范围。

### 3.2 先解决真实阻塞

当前优先级最高的问题是：

- 运行时材料身份错误

不是：

- planner 的“理论纯度”
- 外部存储网络
- 目标产物 NBT 主动指定

### 3.3 每阶段都要有“做什么 / 不做什么 / 完成标准”

没有这三项，阶段边界就会漂移。

- 输出总体方案决议

### 5.5 当前状态

- 已完成

## 六、Phase 1：NBT 标准与共享库存抽象层设计

### 6.1 目标

补齐后续实施最关键的设计输入，形成可以直接指导实现的正式设计方案。

### 6.2 做什么

1. 确认 NBT 身份标准
2. 确认匹配语义
3. 确认事务回退语义
4. 确认不支持场景策略
5. 完成共享库存抽象层设计
6. 完成对象级正式提案：
   - `MaterialKey`
   - `NormalizedMaterialPayload`
   - `MaterialIdentityNormalizer`
   - `MaterialMatcher`
   - `IngredientRequirement`
   - `InventorySource`
   - `InventoryView`
   - `VirtualInventorySnapshot`
   - `ResolvedExecutionPlan`
   - `CraftingTransaction`
7. 完成多轮交叉审阅与修订

### 6.3 不做什么

1. 不写正式实现代码
2. 不升级 `CraftingPlanner` 为 NBT 节点图
3. 不接入外部存储
4. 不扩展入口协议以支持目标产物 NBT 主动指定

### 6.4 完成标准

1. 已有一套正式设计文档，而不是仅有方向性决议
2. 对象职责、边界、交互关系已明确
3. 审阅后不存在明显结构冲突或未决核心歧义
4. 后续实施无需重新争论总体方向

### 6.5 当前状态

- 已完成

当前 `Phase 1` 的正式架构沉淀文档为：

- `docs/architecture/共享库存抽象层.md`

## 七、Phase 2：第一阶段运行时 NBT 方案落地

### 7.1 目标

在不升级 planner 为 NBT 节点图的前提下，完成运行时 NBT 友好链路，使当前最真实的 NBT 阻塞得到解决。

### 7.2 做什么

1. 落地共享库存抽象层
2. 替换当前 `Map<Item, Integer>` 运行时主模型
3. 改造以下模块：
   - `InventoryUtils`
   - `TransactionCalculator`
   - `CraftingTaskExecutor`
   - `CraftingTransaction`
4. 统一以下语义：
   - 预检查
   - 虚拟扣减
   - 正式扣减
   - 缺料分析
5. 增加 NBT 场景测试
6. 保持旧的纯 `Item` 场景不退化

### 7.3 不做什么

1. 不把 planner 升级到 NBT 节点图
2. 不实现目标产物 NBT 主动指定
3. 不实现外部存储正式支持
4. 不一次性追求所有复杂动态组件化物品全覆盖

### 7.4 完成标准

1. 典型 NBT Mod 物品输入匹配正确
2. 虚拟库存与正式执行语义一致
3. 普通缺料与“不支持”用户可见语义区分清楚
4. 原有纯 `Item` 路径不退化
5. 当前阶段范围内的问题可通过固定测试矩阵与手工验证清单复现和回归

### 7.5 当前阶段结论

当前已可将以下结论作为阶段性完成状态：

1. 单来源玩家背包路径已完成运行时 NBT 主链落地
2. `TransactionCalculator` 的核心虚拟搜索主路径已切到 `MaterialKey / MaterialMatcher / VirtualInventorySnapshot`
3. `CraftingTaskExecutor` 已接入请求级 `MISSING / UNSUPPORTED` 结果路径
4. `PlayerInventoryView` 的单来源执行路径已具备：
   - 精确 NBT 选槽
   - revalidate 失败无部分扣减
   - output fallback
5. 核心自动化测试矩阵已可通过

但本阶段的“完成”仅限于：

- **第一阶段、单来源、玩家背包路径**

不应扩大解读为：

- 多来源存储支持已完成
- 目标产物 NBT 主动指定已完成
- planner NBT 图扩展已完成

补充说明：

- 截至 `2026-05-31`，上述“未完成”中的“目标产物 NBT 主动指定”已进入 `Phase 4A` 第一批落地
- 当前已落地部分不仅包含后端契约、执行器/计算器身份传递与 `JEI Ctrl` 递归构包，也包含 GUI 对 JEI runtime 可见变体的补充选择
- 真实运行时 JEI / gameplay 复验仍未完成，因此依然不能把该项视为整体完成

### 7.6 最小验收矩阵

Phase 2 至少必须覆盖以下场景：

1. 纯 `Item` 场景
2. 同一 `Item` 不同 NBT
3. 多候选输入场景
4. recipe 回退场景
5. 请求级失败语义：
   - 缺料
   - 不支持
6. 正式执行一致性
7. 产物发放场景

### 7.7 自动化验证要求

Phase 2 完成前，至少必须具备：

1. 核心运行时逻辑自动化测试
2. 回退语义自动化测试
3. 失败语义聚合自动化测试
4. 一条固定项目级验证命令

交付时必须把可执行命令明确写入文档。

### 7.8 手工验证要求

Phase 2 完成前，必须有固定手工验证清单，至少包括：

1. 典型 NBT 输入成功
2. 错误变体不误扣
3. recipe 回退后无脏状态
4. “缺料”与“不支持”结果可观察且可区分

### 7.9 真实执行原子性要求

Phase 2 第一阶段的真实执行原子性要求限定为：

1. 输入扣减必须精确且先验证后提交
2. 若正式提交前发现库存状态已变化，则整笔执行失败且不发生部分扣减
3. 产物插入失败不触发事务回滚，而进入既定降级路径
4. 第一阶段只承诺单来源玩家背包路径的一致性
5. 不承诺多来源跨容器补偿事务

## 八、Phase 3：方案与代码对照、收口与补强

### 8.1 目标

防止实现阶段偏离规划，并识别残留问题与下一阶段入口。

### 8.2 做什么

1. 对照总体方案决议
2. 对照共享库存抽象层设计文档
3. 识别实现中的偏差、折中与未完成项
4. 补齐必要文档
5. 输出“当前代码 vs 当前方案”的对照结果
6. 明确第一阶段已知保留桥接与下一阶段扩展边界

### 8.3 不做什么

1. 不在对照阶段悄悄扩大范围
2. 不把后续扩展项混入当前阶段补丁

### 8.4 完成标准

1. 方案与代码偏差有明确记录
2. 已知残留点与后续阶段入口清晰
3. 当前阶段收口状态明确
4. Phase 2 的固定验证矩阵已重新执行
5. Phase 2 的固定手工验证清单已重新执行

### 8.5 当前推荐

在当前时间点，`Phase 3` 应作为下一步直接工作重点。

原因：

1. `Phase 2` 第一阶段已经具备阶段性完成结论
2. 当前最需要的是把“代码实际状态”和“方案原始决议”做一次正式对照
3. 只有完成这一轮对照，后续完整方案剩余项才不会发生范围漂移

### 9.4 完成标准

1. 代码已实现第一批目标产物身份指定链路
2. 自动化验证已完成

## 十、阶段衔接规则

当 `Phase 1` 完成后，后续不得再重新争论：

- 是否保留 `Item` 级粗规划
- 是否采用共享库存抽象层
- 是否先解决运行时 NBT 再考虑预计算图

进入 `Phase 2` 后，只允许讨论：

- 如何按设计实现
- 实现中的局部技术难点
- 哪些边界场景暂时保守拒绝

进入 `Phase 3` 后，应优先讨论：

- 当前代码与方案的偏差
- 当前桥接语义是否还可继续收窄
- 下一阶段扩展项的优先级

进入 `Phase 4A` 后，应优先讨论：

- 目标产物身份如何穿过包体、执行器、计算器与 JEI 入口
- 自动化验证是否覆盖成功 / 失败矩阵与旧行为兼容
- 真实运行时验证还有哪些未闭合场景

## 十三、后续推进顺序与决策点

### 13.1 推荐推进顺序

建议按以下顺序继续推进：

1. 先完成 `Phase 4A` 的文档写回与固定自动化 / 手工验证分层
2. 再补齐真实运行时 JEI / gameplay 复验记录
3. 然后启动下一轮扩展规划，优先评估：
   - 原版相邻容器支持
   - 第三方存储兼容策略
   - planner 是否需要局部感知 NBT
4. 最后再决定下一轮实施窗口具体落在哪一个扩展子方案

推荐这个顺序的原因：

1. 当前第一阶段运行时 NBT 路径已经稳定，而 `Phase 4A` 正处于“代码已落地但手工运行时验证未闭合”的状态
2. 只有先把目标产物身份链路的当前真相和验证边界写清楚，后续扩展路线才不会建立在错误假设上
3. 原版相邻容器、第三方存储、planner 延展都属于下一轮范围选择问题，不应混入当前 `Phase 4A` 收口

### 13.2 当前推荐项

当前推荐直接采纳以下默认项：

1. 下一步主任务定为 `Phase 4A` 收口
2. `Phase 4A` 先做文档化写回与真实运行时复验，不再插入额外功能实现
3. 下一轮扩展规划时，优先级建议为：
   - 第一优先级：原版相邻容器支持评估
   - 第二优先级：第三方存储兼容策略评估
   - 第三优先级：planner 局部 NBT 感知评估

### 13.3 已确认的高层优先级

当前已确认：

1. `Phase 4A` 完成真实运行时验证前，不得宣称“目标产物 NBT 主动指定”已经整体完成
2. 外部存储路线坚持“先原版相邻容器，再第三方存储网络”的推进顺序

当前转接与复验时，以 `docs/HANDOFF.md` 与 `docs/Phase4A_运行时验证.md` 为主动路径，不再依赖计划目录中的 handoff 或 checklist。

除上述两点外，其余内容当前均按本路线图默认推荐继续推进。
