# RecursiveCraft 共享库存抽象层

> 目标分支：`1.20.1`
> 文档日期：2026-06-01
> 文档定位：作为运行时 NBT 执行与后续存储扩展的正式共享架构说明

---

## 一、定位

共享库存抽象层是当前 NBT 主线中的正式架构层，负责统一：

1. 运行时材料身份
2. 身份归一化
3. 材料匹配
4. 虚拟库存快照
5. 正式执行桥接

它的目标不是重写 `CraftingPlanner`，而是替代旧的散落式做法，例如：

- `Map<Item, Integer>` 快照
- `countItem(item)` 校验
- `stack.getItem() == item` 扣减
- 多处各自维护的材料匹配逻辑

---

## 二、当前边界

### 2.1 本层负责

1. 定义运行时材料身份模型
2. 定义统一归一化入口
3. 定义统一 matcher 语义
4. 定义正式虚拟库存表达
5. 定义从虚拟事务到真实执行的桥梁
6. 为未来扩展到外部存储保留统一接入点

### 2.2 本层当前不负责

1. 不把 `CraftingPlanner` 升级为 NBT 节点图
2. 不把 planner 粒度从 `Item` 改成 `ItemStack`
3. 不直接承诺第三方存储接入
4. 不承诺多来源跨容器补偿事务

---

## 三、正式设计原则

当前正式原则如下：

1. `MaterialKey` 是唯一正式材料身份
2. `MaterialIdentityNormalizer` 是唯一正式身份归一化入口
3. `MaterialMatcher` 是唯一正式材料语义中心
4. `VirtualInventorySnapshot` 是唯一正式虚拟库存表达
5. `ResolvedExecutionPlan` 是从虚拟事务到真实执行的唯一桥梁
6. 预检查、虚拟扣减、正式扣减必须共享同一 matcher 语义
7. 第一阶段只承诺单来源玩家背包路径的一致性

---

## 四、核心对象与职责

### 4.1 `MaterialKey`

作用：

1. 作为虚拟库存统计主键
2. 作为材料匹配主键
3. 作为正式扣减主键
4. 作为缺料分析主键

正式边界：

1. 由 `Item + 规范化后的功能性载荷` 构成
2. 不直接持有原始 `ItemStack`
3. 必须具备稳定 `equals/hashCode`

### 4.2 `NormalizedMaterialPayload`

作用：

1. 保存规范化后的功能性载荷
2. 避免直接把原始全部组件/NBT 作为身份键

第一阶段原则：

1. 功能性字段保留
2. 无法确认安全忽略的字段保留
3. 是否忽略字段必须显式定义

### 4.3 `MaterialIdentityNormalizer`

作用：

1. 把原始 `ItemStack` 归一化为正式身份
2. 在无法稳定表达时显式返回失败

当前约束：

1. 归一化失败属于 normalizer 责任
2. matcher 不负责临时兜底归一化失败

### 4.4 `IngredientRequirement`

作用：

1. 表达 recipe 输入在运行时的可匹配需求
2. 统一承载精确候选与附加匹配约束

### 4.5 `MaterialMatcher`

作用：

1. 统一材料匹配语义
2. 统一候选级结果
3. 统一请求级结果

当前对外请求级结果只承诺：

1. `MISSING`
2. `UNSUPPORTED`

内部候选级结果仍可保留：

1. `MATCHED`
2. `REJECTED_BY_IDENTITY`
3. `UNSUPPORTED_MATERIAL_SEMANTICS`

### 4.6 `InventorySource`

作用：

1. 表示一个真实库存来源
2. 提供快照、精确扣减和插入能力

当前来源：

1. 玩家背包

后续来源：

1. 原版容器
2. 第三方存储接口

### 4.7 `VirtualInventorySnapshot`

作用：

1. 作为运行时搜索阶段的正式虚拟库存表达
2. 保存 `MaterialKey` 聚合总量
3. 提供 `Item -> MaterialKey` 辅助索引

### 4.8 `InventoryView`

作用：

1. 把一个或多个 `InventorySource` 聚合为统一视图
2. 生成运行时虚拟快照
3. 生成正式执行计划
4. 提交正式执行计划

当前虽然主要是单来源，但接口不应写死成只支持单来源。

### 4.9 `ResolvedExecutionPlan`

作用：

1. 把虚拟事务中的材料身份绑定到真实槽位
2. 支持正式提交前 revalidate
3. 防止提交时重新扫描并选中另一组栈

### 4.10 `CraftingTransaction`

作用：

1. 表达逻辑层面的事务结果
2. 由执行计划桥接到真实库存执行

当前边界：

1. 输入侧围绕 `MaterialKey`
2. 输出侧以真实 `resolvedOutputs` 为准

## 五、运行时流程

### 5.1 虚拟搜索阶段

1. `InventoryView.snapshot()` 生成 `VirtualInventorySnapshot`
2. `MaterialIdentityNormalizer` 归一化库存与目标栈
3. `MaterialMatcher.requirementOf()` 生成运行时输入需求
4. `TransactionCalculator` 在虚拟库存上执行候选尝试
5. ingredient 可试探，recipe 是最小提交/回退单元

### 5.2 正式执行阶段

1. 基于 `CraftingTransaction` 与真实库存生成 `ResolvedExecutionPlan`
2. 提交前 revalidate 所有 `ResolvedConsumption`
3. 若 revalidate 失败，则整笔执行失败且不发生部分扣减
4. 输入扣减成功后，再按 `resolvedOutputs` 做产物投放
5. 产物投放失败不回滚输入扣减，而进入既定 fallback

---

## 六、当前正式原子性语义

第一阶段采用：

- **输入扣减原子性 + 产物投放降级容错**

即：

1. 输入侧先验证后提交
2. 提交前库存变化则整笔失败
3. 不发生部分输入扣减
4. 产物插入失败不回滚输入扣减
5. 当前只承诺单来源玩家背包路径一致性

---

## 七、与后续存储支持的关系

共享库存抽象层解决的是：

- “物品身份如何定义”

后续存储扩展解决的是：

- “物品从哪里来”

因此后续存储支持必须消费这层抽象，而不是绕过它再造一套旧式 `Map<Item, Integer>` 多来源逻辑。正式存储路线见 `docs/architecture/存储支持与适配路线图.md`。
