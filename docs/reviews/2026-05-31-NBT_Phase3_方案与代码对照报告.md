## 一、结论摘要

当前代码状态已经足以支撑以下当前结论：

1. `Phase 2` 第一阶段“单来源玩家背包路径”的运行时 NBT 主链已经落地。
2. 当前实现与既定总体方案在主线上保持一致：
   - 保留 `CraftingPlanner` 的 `Item` 级粗规划职责。
   - 将运行时材料身份切换为 `MaterialKey` 主导。
   - 将虚拟库存、匹配、正式执行桥接为一套统一链路。
3. `Phase 4A` “目标产物身份主动指定”第一批实现已经落地，并已补齐关键 runtime 身份链路证据。
4. 当前尚未进入外部存储范围；方块模式相邻容器与第三方存储支持继续保留为后续独立主题，而不是本轮 NBT 收口 blocker。
5. 当前最适合的收口动作，不是继续扩张功能面，而是把当前头提交的方案-代码对照、验证结论和后续边界固定下来。

## 三、当前仍保留的桥接项与折中实现

### 3.1 `CraftingTransaction` 仍保留部分 `Item` 聚合桥接，但边界已继续收紧

当前 `CraftingTransaction` 虽然已经新增：

- `materialNeeds`
- `resolvedOutputs`
- `unsupported`

但仍保留以下旧桥接：

1. `needs: Map<Item, Integer>`
2. `getProvides()` 兼容访问口

证据：

- `common/src/main/java/xczl/recursivecraft/data/CraftingTransaction.java:13-16`
- `.../CraftingTransaction.java:20-27`

评估：

- 旧的 `getNetDeltas()` 与 `execute(Player)` 已从代码中移除，事务对象不再承担旧执行职责。
- `provides` 已不再作为独立状态保存，而是由 `resolvedOutputs` 现算得出。
- `needs` 也已从“总需求镜像”进一步收紧为“仅 unresolved 的 item-level missing deficits”，不再记录已被虚拟库存满足的消费。
- 当前残留的是数据聚合层面的最小 `Item` 级桥接，而不再是独立输出状态源或总消费镜像。
- 这仍会影响对象边界清晰度，属于后续可继续收窄的残留。

### 3.2 `CraftingTaskExecutor` 仍有 `Item` 级目标产出桥接，但旧浅层缺料分析支路已移除

当前 `CraftingTaskExecutor` 的主执行路径已经接入：

- `PlayerInventoryView`
- `DefaultMaterialIdentityNormalizer`
- `DefaultMaterialMatcher`

证据：

- `common/src/main/java/xczl/recursivecraft/core/CraftingTaskExecutor.java:151-168`

但仍保留以下桥接或旧逻辑：

1. `NetChanges.provides` 仍按 `Map<Item, Integer>` 检查目标产出
   - 证据：`.../CraftingTaskExecutor.java:28-35`、`119-126`、`136-139`

评估：

- 第一项属于第一阶段可接受桥接，因为目标产物主动指定 NBT 还未进入本期范围。
- 旧的 `reportMissingMaterials()` 与 `InventoryUtils.snapshot()` 支路已经从主代码中移除，不再构成当前阶段的保留缺口。

### 3.3 对外失败语义已收口到既定请求级可见边界

评估：

- 这一项已经按既定设计收口完成。
- 当前残留问题不再是用户可见失败语义本身，而是更深层的执行桥接与扩展边界。

### 3.4 `TransactionCalculator` 与 `PlayerInventoryView` 的快照逻辑重复已收口

- 当前共享库存抽象层在“单来源玩家背包快照构造”上已经具备单一事实来源。

### 3.5 `MaterialMatcher.aggregate(...)` 已进入主流程，但 `RuntimeMatchClause` 仍为保留骨架

### 3.6 `PlayerInventoryView.planExecution()` 仍属于第一阶段可工作桥接版

证据：

- `common/src/main/java/xczl/recursivecraft/runtime/inventory/PlayerInventoryView.java:42-60`

评估：

- 这条路径在当前第一阶段是可工作的。
- 但它并没有把搜索阶段更丰富的候选选择上下文直接带入执行桥梁。
- 因此它应被记录为第一阶段保留桥接，而不是误判为最终形态。

4. 把“设计已承诺但代码仍保留桥接”的点登记为后续收窄项

### 5.2 当前不建议混入的内容

1. 不在当前收口阶段直接推进外部存储实现
2. 不在当前收口阶段直接把方块模式容器支持混回 NBT 主线完成标准
3. 不在当前收口阶段直接推进 planner 的 NBT 感知扩展

## 六、后续边界

就当前 NBT 运行时主线而言：

1. 单来源玩家背包路径 + `Phase 4A` 目标产物身份指定已经完成当前范围收口。
2. 后续若继续扩张，将转入独立主题，而不再属于“当前 NBT 主线是否可用”的收口判断。

后续独立主题可按以下顺序考虑：

1. 当前头提交下的正式可用性测试与回归
2. 方块模式相邻原版容器支持
3. 第三方存储兼容策略
4. planner 是否需要局部感知 NBT

## 七、总评

当前代码状态可以概括为：

- 主路线正确。
- 第一阶段核心目标已达到收口标准。
- `Phase 4A` 关键 runtime 身份链路已补齐真实证据。
- 旧执行路径、旧缺料分析支路和对外失败语义已完成一轮代码收口。
- 仍存在少量最小 `Item` 级桥接，以及被明确保留到后续主题的 `RuntimeMatchClause` 骨架问题。

因此，当前最合理的结论不是继续扩张实现面，而是：

1. 当前头提交下的 NBT 运行时主线已经可以按当前范围收口
2. 应先进行正式可用性测试，再决定是否开启存储扩展主题
3. 后续扩展不应再被表述为“当前 NBT 是否完成”的前置条件
