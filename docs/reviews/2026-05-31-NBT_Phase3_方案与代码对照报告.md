## 一、结论摘要

当前代码状态已经足以支撑以下阶段性结论：

1. `Phase 2` 第一阶段“单来源玩家背包路径”的运行时 NBT 主链已经落地。
2. 当前实现与既定总体方案在主线上保持一致：
   - 保留 `CraftingPlanner` 的 `Item` 级粗规划职责。
   - 将运行时材料身份切换为 `MaterialKey` 主导。
   - 将虚拟库存、匹配、正式执行桥接为一套统一链路。
3. 当前尚不能把状态扩大表述为“NBT 完整方案完成”。
4. 当前最适合进入 `Phase 3` 的工作，不是继续扩张功能面，而是对既有实现做正式对照、验证收口与桥接收窄评估。

## 三、当前仍保留的桥接项与折中实现

### 3.1 `CraftingTransaction` 仍保留旧 `Item` 聚合桥接

当前 `CraftingTransaction` 虽然已经新增：

- `materialNeeds`
- `resolvedOutputs`
- `unsupported`

但仍保留以下旧桥接：

1. `needs: Map<Item, Integer>`
2. `provides: Map<Item, Integer>`
3. `getNetDeltas()`
4. `execute(Player player)`

证据：

- `common/src/main/java/xczl/recursivecraft/data/CraftingTransaction.java:25-30`
- `.../CraftingTransaction.java:86-102`
- `.../CraftingTransaction.java:109-164`

评估：

- 这些桥接不再是第一阶段主执行路径的核心依赖。
- 但它们仍然会影响代码可读性、对象职责边界和后续扩展时的误用风险。
- 这属于 `Phase 3` 应优先评估收窄的对象级残留。

### 3.2 `CraftingTaskExecutor` 仍有 `Item` 级产出检查与浅层缺料分析

当前 `CraftingTaskExecutor` 的主执行路径已经接入：

- `PlayerInventoryView`
- `DefaultMaterialIdentityNormalizer`
- `DefaultMaterialMatcher`

证据：

- `common/src/main/java/xczl/recursivecraft/core/CraftingTaskExecutor.java:151-168`

但仍保留以下桥接或旧逻辑：

1. `NetChanges.provides` 仍按 `Map<Item, Integer>` 检查目标产出
   - 证据：`.../CraftingTaskExecutor.java:28-35`、`119-126`、`136-139`
2. `reportMissingMaterials()` 仍基于 `InventoryUtils.snapshot()` 和 `Ingredient.getItems()` 做浅层 `Item` 级消耗
   - 证据：`.../CraftingTaskExecutor.java:175-247`

评估：

- 第一项属于第一阶段可接受桥接，因为目标产物主动指定 NBT 还未进入本期范围。
- 第二项属于明显的“旧分析支路未同步升级”，应在 `Phase 3` 标记为保留缺口。

### 3.3 对外失败语义尚未完全收口到既定承诺

设计对外只承诺用户可见语义：

1. `MISSING`
2. `UNSUPPORTED`

但当前真实执行失败路径仍会把内部状态直接暴露给用户：

1. `FAILED_REVALIDATION`
2. `FAILED_CONSUME`

证据：

- `common/src/main/java/xczl/recursivecraft/runtime/execution/ExecutionCommitResult.java:18-27`
- `common/src/main/java/xczl/recursivecraft/core/CraftingTaskExecutor.java:157-165`

评估：

- 这不是主链阻塞问题，但属于设计与实现之间仍需收口的偏差。
- `Phase 3` 应明确：是保留这些内部状态为外显语义，还是把它们统一折叠回既定请求级结果。

### 3.4 `TransactionCalculator` 与 `PlayerInventoryView` 之间仍存在快照逻辑重复

当前存在两套玩家背包快照构造逻辑：

1. `TransactionCalculator.snapshotPlayerInventory()`
   - 证据：`common/src/main/java/xczl/recursivecraft/core/TransactionCalculator.java:480-499`
2. `PlayerInventoryView.snapshot()`
   - 证据：`common/src/main/java/xczl/recursivecraft/runtime/inventory/PlayerInventoryView.java:26-39`

评估：

- 两者当前语义接近，未构成显性功能错误。
- 但它削弱了“共享库存抽象层作为唯一正式库存入口”的设计目标。
- 这属于 `Phase 3` 需要登记的结构性重复，而不一定要求本阶段立即重构。

### 3.5 `MaterialMatcher` 与 `RuntimeMatchClause` 仍有预留骨架未完全进入主流程

当前 `MaterialMatcher` 接口与 `RuntimeMatchClause` 对象已经存在，但仍有两层未完全收口：

1. 请求级 `MISSING / UNSUPPORTED` 聚合仍主要在 `TransactionCalculator` 中手工推进，而不是显式走 `MaterialMatcher.aggregate(...)`
2. `RuntimeMatchClause` 当前更接近预留骨架，生产侧尚未形成真正的 clause 输出链

证据：

- `common/src/main/java/xczl/recursivecraft/runtime/match/MaterialMatcher.java`
- `common/src/main/java/xczl/recursivecraft/runtime/match/DefaultMaterialMatcher.java:53-58`
- `common/src/main/java/xczl/recursivecraft/runtime/match/RuntimeMatchClause.java`
- `common/src/main/java/xczl/recursivecraft/core/TransactionCalculator.java:181-230`
- `common/src/main/java/xczl/recursivecraft/core/TransactionCalculator.java:328-360`

评估：

- 这不影响第一阶段功能成立。
- 但它说明“matcher 作为唯一正式语义中心”在代码里尚未完全收紧到设计终态。

### 3.6 `PlayerInventoryView.planExecution()` 仍属于第一阶段可工作桥接版

当前 `planExecution()` 会基于 `transaction.getMaterialNeeds()` 反推一个“单 `MaterialKey` requirement”，再逐槽扫描真实背包。

证据：

- `common/src/main/java/xczl/recursivecraft/runtime/inventory/PlayerInventoryView.java:42-60`

评估：

- 这条路径在当前第一阶段是可工作的。
- 但它并没有把搜索阶段更丰富的候选选择上下文直接带入执行桥梁。
- 因此它应被记录为第一阶段保留桥接，而不是误判为最终形态。

## 五、Phase 3 收口建议

### 5.1 当前应优先推进的收口项

1. 补齐 `Phase 2` 手工验证清单与复验记录
2. 明确 `FAILED_REVALIDATION / FAILED_CONSUME` 是否继续作为用户可见结果
3. 评估 `CraftingTransaction` 中旧 `Item` 聚合桥接的保留边界
4. 评估 `reportMissingMaterials()` 是否需要迁移到运行时材料身份语义
5. 评估 `MaterialMatcher.aggregate(...)` 与 `RuntimeMatchClause` 是否在当前阶段就要继续收紧，还是明确保留到下一轮
6. 把当前“设计已承诺但代码仍有桥接”的点单独登记为后续收窄项

### 5.2 当前不建议混入的内容

1. 不在 `Phase 3` 收口阶段直接推进外部存储实现
2. 不在 `Phase 3` 收口阶段直接推进目标产物 NBT 主动指定
3. 不在 `Phase 3` 收口阶段直接推进 planner 的 NBT 感知扩展

## 六、后续扩展优先级

已确认后续扩展优先级为：

1. 目标产物 NBT 主动指定
2. 原版相邻容器支持
3. 第三方存储兼容策略
4. planner 是否需要局部感知 NBT

外部存储路线已确认优先顺序为：

1. 先原版相邻容器
2. 后第三方存储网络

---

## 七、总评

当前代码状态可以概括为：

- 主路线正确。
- 第一阶段核心目标已达到阶段性完成标准。
- 仍存在少量旧桥接、浅层旧支路与语义外显边界未完全收口的问题。

因此，当前最合理的直接任务不是继续扩张实现面，而是：

1. 完成 `Phase 3` 的正式收口
2. 固化验证与偏差记录
3. 再按已确认优先级进入下一轮扩展规划
