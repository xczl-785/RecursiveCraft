# RecursiveCraft NBT 支持调研报告

> 调研日期：2026-05-31
> 目标分支：`1.20.1`
> 调研范围：当前递归合成链路中的库存建模、材料匹配、事务执行、缺料分析，以及未来与外部存储支持的耦合关系

---

## 一、调研结论

当前版本的 RecursiveCraft 在“按物品类型递归规划与执行合成”这一目标上已经可以正常工作，但对大量依赖 NBT 的 Mod 物品兼容性不足。其根本原因并不在单个判断分支，而在于系统当前将库存抽象为 `Map<Item, Integer>`，默认同一 `Item` 的全部实例都可互换。

因此，若要支持：

1. NBT 区分的同类物品
2. 耐久、附魔、自定义数据不同的实例
3. 某些配方对特定数据物品的精确消费

则必须先引入一层新的库存抽象，替代目前“只按 `Item` 聚合计数”的模型。

本报告的推荐方案为：

- 先建立共享抽象层，统一库存读取、匹配、预扣减与事务落地接口
- 在该抽象层上优先落地 NBT 支持
- 后续存储支持沿用同一抽象层扩展“来源”，而不是重新设计一套外部库存模型

---

## 二、当前现状

### 2.1 当前系统如何建模库存

当前代码对库存的核心抽象是“某个 `Item` 有多少个”，而不是“有哪些具体 `ItemStack`”。

直接证据如下：

- `InventoryUtils.snapshot(Container)` 返回 `Map<Item, Integer>`，并在遍历容器时使用 `stack.getItem()` 聚合数量
- `TransactionCalculator.CalcContext` 的虚拟库存字段类型为 `Map<Item, Integer>`
- `CraftingTaskExecutor` 在执行前的材料校验中使用 `player.getInventory().countItem(entry.getKey())`
- `CraftingTransaction.execute()` 在实际扣除物品时按 `stack.getItem() == item` 顺序扣减

这意味着：

- 同一 `Item` 的不同 NBT 实例会被压平成一条记录
- 对“同一物品、不同数据”的材料需求无法表达
- 事务层面只能记录“消耗几个该物品”，无法记录“消耗哪个具体栈”

### 2.2 当前系统在哪些阶段丢失 NBT 信息

NBT 信息的丢失并不是只发生一次，而是贯穿整条链路：

1. **库存快照阶段**
   - `ItemStack -> Item + count`
   - NBT、耐久、自定义名称、附魔等全部被抹平

2. **递归计算阶段**
   - 虚拟库存以 `Map<Item, Integer>` 为单位流转
   - 子材料匹配只能基于 `Item`

3. **缺料分析阶段**
   - 缺料报告按 `Ingredient.getItems()` 的物品选项做贪心消费
   - 无法区分“有这个物品，但不是正确的 NBT 版本”

4. **事务执行阶段**
   - 实际扣除时通过 `stack.getItem() == item` 删除
   - 可能错误消耗错误实例

### 2.3 当前系统为什么对原版和部分 Mod 还能正常工作

因为很多配方在实际运行时满足以下条件：

- 输入产物主要依赖 `Item` 类型，不区分 NBT
- 物品虽然有 NBT，但配方不要求精确匹配该 NBT
- 玩家背包中同类物品往往本来就没有多种变体混放

因此，“功能正常”并不代表模型已经覆盖复杂 Mod 场景，只能说明当前命中的使用面还没有彻底穿透这一限制。

## 三、问题本质

### 3.1 这不是单点 Bug，而是身份模型不足

如果只在某几个判断处额外加上 `NBT` 比较，仍然无法解决问题。原因是当前系统缺的不是“比较逻辑”，而是“库存单位”。

当前库存单位是：

- `Item`

而 NBT 兼容所需的库存单位至少应升级为以下两类之一：

1. **具体栈视角**
   - 以 `ItemStack` 或其规范化副本作为单位
   - 优点：表达力完整
   - 缺点：事务与匹配逻辑复杂度高

2. **可匹配键视角**
   - 用一个 `StackKey` / `MaterialKey` 封装：
     - `Item`
     - 可选 NBT
     - 可选耐久策略
     - 可选附加匹配策略
   - 优点：可控、可扩展、便于逐步迁移
   - 缺点：需要专门设计键规范与匹配规则

### 3.2 “先做 NBT”并不意味着先大面积重写规划器

需要区分两层问题：

- **配方规划层**
  - 当前 `CraftingPlanner` 计算的是物品层面的最优路径和理论成本
- **库存匹配与执行层**
  - 当前 `TransactionCalculator` 与 `CraftingTransaction` 负责材料消耗、虚拟库存推进和实际扣除

在多数情况下，NBT 兼容优先影响的是第二层，而不是第一层。

这意味着可以采用更稳妥的策略：

- 规划器仍按 `Item` 建立候选路径
- 真正决定“背包里哪些材料可用、该扣哪个栈”的逻辑，迁移到新的抽象层中

这样可以避免第一步就把整个递归规划算法升级为“NBT 级图搜索”。

## 四、共享前置：库存抽象层

### 4.1 该抽象层为什么属于 NBT 与存储支持的共同前置

NBT 支持需要回答两个问题：

1. 某个材料需求该匹配哪些具体物品栈
2. 匹配成功后该如何在虚拟库存与真实库存中扣减

存储支持需要回答两个问题：

1. 物品不只来自玩家背包，还可能来自箱子、漏斗、其他存储
2. 多个库存来源如何统一快照、统一匹配、统一提交事务

这两类问题虽然切入角度不同，但都依赖一个共同基础：

- “库存读取与匹配”不能再被写死为 `player.getInventory()` + `Map<Item, Integer>`

因此，共享抽象层应优先服务于 NBT，但设计时必须允许未来接入多个库存来源。

### 4.2 推荐的抽象方向

建议引入以下概念，而不是继续在现有工具类上堆条件判断：

#### 1. `InventorySource`

表示一个实际库存来源，例如：

- 玩家背包
- 方块实体容器
- 兼容的第三方存储接口

职责：

- 枚举可见物品栈
- 按匹配规则尝试扣除
- 接收事务产物

#### 2. `InventoryView`

表示若干 `InventorySource` 组合后的统一视图。

职责：

- 生成虚拟快照
- 暴露统一的查询与消费接口
- 屏蔽“来自哪个容器”的差异

#### 3. `StackKey`

表示某类材料在系统中的“匹配身份”。

第一阶段建议具备以下字段：

- `Item item`
- `@Nullable CompoundTag normalizedTag`
- `MatchMode mode`

其中 `MatchMode` 至少支持：

- `ITEM_ONLY`
- `ITEM_AND_TAG`

后续如果确实需要，再扩展：

- 忽略部分 Tag 路径
- 忽略耐久
- 自定义兼容规则

#### 4. `MaterialMatcher`

负责定义：

- 一个 `Ingredient` 如何转换为可匹配条件
- 一个 `ItemStack` 是否满足某个材料需求

这样可以把“匹配规则”从事务逻辑中拆出去，避免 `TransactionCalculator` 进一步膨胀。

### 4.3 为什么不建议继续沿用 `Map<Item, Integer>`

因为它会迫使后续所有 NBT 逻辑都变成“例外处理”：

- 先按 `Item` 统计
- 再在某处回头修正某些 NBT 特例
- 最终导致预检、缺料分析、正式执行三套规则不一致

一旦发生这种情况，系统最常见的问题不是“不能合成”，而是：

- 预检查通过，但执行扣错物品
- 缺料报告说不缺，实际执行失败
- 某些配方成功，某些配方随机失败

## 五、可行方案评估

### 方案 A：直接在现有逻辑上局部补 NBT 判断

#### 做法

- 在 `hasEnoughMaterials()`、`consumeOneMatchingItem()`、`CraftingTransaction.execute()` 等位置补充对 NBT 的判断

#### 优点

- 改动表面上较小
- 可以快速试错

#### 缺点

- 根模型不变
- 预检查、虚拟库存、实际执行之间容易出现不一致
- 后续接外部存储时会再复制一遍问题

#### 结论

不推荐。只能用于临时性验证，不适合作为正式方案。

### 方案 B：先建立共享抽象层，再在库存匹配层支持 NBT

#### 做法

- 引入 `InventorySource`、`InventoryView`、`StackKey`、`MaterialMatcher`
- 先让 `TransactionCalculator` 与 `CraftingTaskExecutor` 改为依赖抽象层
- 第一阶段保持规划器继续按 `Item` 工作
- 第二阶段让匹配与扣减基于 `StackKey`

#### 优点

- 能控制改动范围
- 对未来存储支持复用价值高
- 允许分阶段迁移

#### 缺点

- 首轮抽象设计要足够克制
- 需要同步修正测试基线

#### 结论

推荐。这是当前项目最稳妥的工程方案。

### 方案 C：将整个递归规划器全面升级到 `ItemStack`/NBT 级

#### 做法

- 让 `CraftingPlanner`、`TransactionCalculator`、事务模型全部按具体栈或 NBT 键运行

#### 优点

- 理论上表达能力最完整

#### 缺点

- 成本极高
- 循环依赖、成本比较、候选路径排序都会复杂化
- 当前项目阶段不适合直接进入这一复杂度

#### 结论

当前不推荐。

## 六、推荐方案

### 6.1 推荐路径

推荐采用“抽象层先行，NBT 优先落地”的两阶段方案：

#### 阶段一：抽象层落地

目标：

- 让新代码不再直接依赖 `Map<Item, Integer>`
- 让“背包读取、虚拟库存、实际扣除”都经过统一入口

范围：

- `InventoryUtils`
- `TransactionCalculator`
- `CraftingTaskExecutor`
- `CraftingTransaction`

阶段结果：

- 系统已经具备未来同时承接 NBT 与存储支持的接口基础

#### 阶段二：NBT 匹配与事务落地

目标：

- 让材料匹配至少支持 `Item + Tag`
- 让实际消耗与预检查遵循同一套规则

范围：

- 缺料分析
- 虚拟库存消费
- 实际事务执行
- 必要时补充 NBT 相关测试夹具

阶段结果：

- 当前最主要的 Mod 兼容性阻塞得到解决

### 6.2 推荐的边界控制

建议第一轮 NBT 支持只承诺：

- 支持精确 `Item + NBT` 匹配
- 不处理过于复杂的“忽略部分 Tag 字段”的定制规则
- 不在第一轮兼容所有第三方存储网络

原因是：

- 当前最紧急的问题是“很多物品被当成同一种”
- 先把最基本的身份问题解决，收益最高
- 若第一轮就引入可配置的 Tag 忽略策略，会显著放大测试与维护复杂度

---

## 七、风险与注意事项

### 7.1 主要风险

1. **预检查与执行规则不一致**
   - 若抽象层只改一半，会出现判断通过但执行失败

2. **缺料分析误导**
   - 若缺料分析继续按 `Item`，而正式执行按 `Item + Tag`，提示会失真

3. **事务模型表达不足**
   - 若事务仍只记录 `Map<Item, Integer>`，最终还是无法精确扣除

4. **测试覆盖不足**
   - 当前测试主要围绕普通物品路径，NBT 场景几乎没有现成覆盖

### 7.2 实施原则

- 不要在现有逻辑上堆叠 NBT 特判
- 抽象层必须先统一“读、判、扣”
- 预检查、虚拟消费、正式执行必须共享同一匹配语义
- 若某些复杂 NBT 规则暂不支持，必须在文档与提示中明确说明

---

## 八、建议的后续工作

1. 先编写一份“库存抽象层设计草案”，明确接口、职责与迁移顺序
2. 在不引入外部存储的前提下，先让玩家背包链路切换到抽象层
3. 为典型 NBT 物品补充回归样例：
   - 同物品不同 NBT
   - 可堆叠带 Tag 物品
   - 不可堆叠但带数据物品
4. 在 NBT 路径稳定后，再接入方块容器与第三方存储

---

## 九、最终建议

NBT 支持已经不是可选优化，而是当前 Mod 兼容性的主要阻塞点。若继续沿用 `Map<Item, Integer>` 作为系统核心库存模型，则无论后续叠加多少补丁，都只能缓解个别场景，不能真正解决问题。

因此，本报告建议：

- 将“库存抽象层”视为 NBT 与存储支持的共同前置
- 由 NBT 需求驱动该抽象层落地
- 在抽象层完成后，优先完成玩家背包链路的 NBT 支持
- 外部存储支持留待同一抽象层复用，不另起一套库存模型
